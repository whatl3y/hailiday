# Hailiday: traceability matrix

This matrix connects every requirement of the US Release to the plan section that says how it is met, the specification sections that define it, the decisions that shape it, the backlog items that build it and the gate evidence that proves it. It also records where the plan reads the words of the original request in a narrower or more specific way than a literal reading, so the product owner can confirm or correct each reading. Use it to check that nothing the user asked for was dropped, to find everything an engineer must read for one requirement, and to see which gate shows that a requirement is satisfied.

**Owns:** requirement traceability (REQ and NFR to plan, specifications, decisions, backlog items and gates); interpretations of the brief.
**Baseline:** planning baseline 2026-11-09; external facts retrieved 2026-11-08.

## How to read this matrix

Requirement IDs and their wording are owned by [PLAN §2](PLAN.md#2-requirements): REQ-01 to REQ-11 come from the user's request ([original_prompt.txt](original_prompt.txt)) and the Fixed decisions D-01 to D-07; REQ-12 is the product thesis the user added on 2026-11-09 (Fixed D-49); NFR-01 to NFR-09 are derived from building the product responsibly. This file abbreviates each requirement and never changes its meaning.

| Column | What it holds | Normative text |
| --- | --- | --- |
| Plan | The PLAN section that states how the requirement is met | [PLAN](PLAN.md) |
| Specifications | The sections an implementer must read; each link points at the file that owns that topic | The linked section |
| Decisions | Decision IDs with their status (Fixed, Proposed, Open). Fixed decisions are requirements and are never reopened here; an Open decision names the default in force | [Decision register](decisions.md#decision-register) |
| Backlog items | The items that build or decide the requirement, grouped by the delivery phase they sit under; IDs follow the [backlog item prefixes](glossary.md#backlog-item-prefixes) | [Backlog](backlog.md) |
| Gate evidence | The artifact in a gate checklist that checks the requirement, with the item that produces it | [Gates](backlog.md#gates) |

Reading rules:

- A requirement is met for the US Release when every listed backlog item is Done under the [definition of done](backlog.md#definition-of-done) and the listed gate evidence exists with its `fixture`, `replay` or `live` label. Fixture evidence shows a requirement is *engineering-complete*; only `live_private` evidence shows it is *live-validated*; a public path is *publicly activated* when its capability is `live_public` ([scope and delivery terms](glossary.md#scope-and-delivery-terms)).
- Where the plan reads a phrase of the brief rather than taking it literally, the reading, its reason and where it is decided are in [Interpretations of the brief](#interpretations-of-the-brief). The product owner confirms or corrects each one in backlog item P01 ([Phase 0](backlog.md#phase-0-decide-and-prepare)). No interpretation reverses a Fixed decision.
- Gates are decision points, not phases. Which requirements each gate's evidence checks is in [Coverage by gate](#coverage-by-gate); the checklists themselves live only in the [backlog](backlog.md#gates).
- Maintenance: a new specification section, backlog item or decision that serves a requirement is added to that requirement's row in the same change. A requirement with no backlog item or no gate evidence is a gap to close, not a note to leave. When two documents disagree, the owner file named in the README's document map wins ([conventions](README.md#conventions)).

Reading paths:

- **Product owner.** Read [Interpretations of the brief](#interpretations-of-the-brief) first and confirm or correct each row in P01; then use the Decisions column to find the Proposed and Open decisions behind each requirement.
- **Engineer or coding agent.** Take the requirement you are implementing, read every section in its Specifications column, then open its backlog items for acceptance criteria; the Gate evidence column tells you what artifact your work must produce.
- **Preparing or deciding a gate.** Use [Coverage by gate](#coverage-by-gate) to see which requirements the gate package must cover, then the backlog checklist for the pass rule.

## Coverage by gate

Each gate is decided by the product owner, advised by the engineering lead, and its outcome is a dated entry in the [decision log](decisions.md#decision-log) ([PLAN §11](PLAN.md#11-delivery-phases-and-gates)). The checklists, triggers, pass rules and failure branches live only in the backlog: [Gate A](backlog.md#gate-a-feasibility-and-provider-decision), [Gate B](backlog.md#gate-b-both-paths-complete), [Gate C](backlog.md#gate-c-private-pilot-readiness), [Gate D](backlog.md#gate-d-public-rollout-readiness). The matrix below shows which requirement each gate's evidence checks and the item that produces the artifact; a dash means the gate does not check that requirement. Every artifact carries its `fixture`, `replay` or `live` label, and a gate package reports fixture and live evidence separately.

| --- | --- | --- | --- | --- |

What a gate deliberately does not require, so that no requirement is blocked by work that belongs elsewhere:

| Gate | Not required to pass | Why |
| --- | --- | --- |
| Gate A | Any live Street View pixel; any built product surface; any merchant approval | The benchmark runs on the permissioned corpus and its Street View-shaped arm; the gate's licensing output is the parameter sheet for the request brief, not a grant |
| Gate B | Live evidence of any kind; merchant approval; review tooling | Fixture-mode completion of both paths is the definition of engineering-complete; live validation is reported separately and later |
| Gate C | Any live Street View pixel; any approved merchant program; the Gate D legal deliverables (accessibility statement, DMCA agent) | The pilot runs under whatever `street_view_ai` state is recorded; shopping tasks can run over a clearly labeled prototype panel if no program is active |
| Gate D | Any merchant program status; `street_view_ai` at `live_public` | Commerce activates per program after the gate (L04); the interim experience is a complete public address path |
